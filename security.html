Prototype · security goals

Security and human approval

Autonomous software should not operate with unchecked authority. Courier aims for fail-closed checks, human gates for consequential actions, and re-verifiable receipts. This page describes goals and the evidenced prototype — not a finished certification.

Five goals of the prototype

1. Fail-closed on unknown outcomes
When evidence is missing or a run is unclear, the system should not assume success. Blocked or unknown states are preferred over blind retries.
2. No autonomous spending on this site
This website has no checkout and no payment processing. Budget limits and human approval remain product goals for consequential cloud spend.
3. Keep personal data off public ledgers
Public pages and demos must not publish customer contact details or secrets. Legal notices live on Impressum and Datenschutz.
4. Least privilege where workers run
Workers should use short-lived, scoped credentials. Full isolation packaging is planned — not a shipped clean-machine product claim.
5. Verifiable receipts
Completed prototype runs should leave a receipt that can be re-checked from files (see PR #361). Retention for any future paid review service will be stated at booking time — no fixed public delivery SLA here.

Repository data handling (concept)

For a future Repo Reality Check style review of public repositories:

  • Read-only intent: Inspect public GitHub repositories without requesting write permissions or deploy keys.
  • No blind code execution: Prefer static review over running untrusted project scripts.
  • Delete working copies: Working trees should be removed after a report is delivered — exact retention stated per engagement.
